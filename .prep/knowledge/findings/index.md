* [Near-tune verdict totals exclude boundary cases; strict criterion still fails](/findings/01M575J12NRTQEV133HK1VG1R0.md) - Checker independently ran poly_eval resolved 200 for all scenarios and compared with pre-FFT commit 7024e56^: reported error quantiles, misses and verdict totals match. However crates/tuner-core/examples/poly_eval.rs only judges truths more than 1.5 cents away from the +/-5-cent in-tune boundary. To reproduce the acceptance gap, copy the native workspace into an ignored directory under target, change that guard to if true, restrict scenario selection to name equality, and run cargo run --quiet --release --manifest-path target/review-strict/Cargo.toml -p tuner-core --example poly_eval resolved 200 "near ±10". With current core, guitar B3 has 3/200 wrong verdicts and E4 5/200; guitar E2-G3 and all ukulele strings have zero. Example: E4 truth +4.6503 cents estimates +5.2500, producing sharp instead of in tune; B3 truth -5.2013 estimates -4.7500, producing in tune instead of flat. Criterion 6 says every played verdict matches, without a boundary exclusion. It remains unmet until implementation meets it or the user settles an explicit tolerance; the checker did not change the requirement. Synthetic evidence still cannot replace criterion 4 real recordings.
* [Strum window lengths: what each instrument needs](/findings/01M7W8BB03RVHZYZMBM084PWGG.md) - poly_eval near ±10 (200 strums): ukulele pitch errors p90 <= 0.24 c even at 4096 samples (85 ms); guitar needs 16384 (8192: D3 29/146 wrong verdicts, E2 p90 1.9 c). presence_eval: ukulele presence reliable from 16384 (8192 misses 13/158 played G4; 4096 misses up to half), guitar validated at 32768. chord_eval (30 ukulele chords x 20, 48 kHz): chord name 97-98% at 8192, ~100% at 12288-16384; exact tab ~95% (misses are equivalent fingerings of the same notes, e.g. E 4442 vs 1402); ~2.5 ms native per chord analysis. All synthetic; real recordings still pending.
* [Peak prominence must be one-sided for semitone neighbours](/findings/01M7X4J4BH6W4SRD8SQ774HNZW.md) - chord.rs find_peaks compared a peak with the median of both sides; a note a semitone above another (F4 over E4 in Fmaj7 2413) had half its neighbourhood inside the lower note's main lobe and was dropped, so Fmaj7 read as 5458 (F5) in ~1/3 of strums. Using the quieter side's median fixed it: chord_eval notes 99.0 -> 100% at 16384, 90 -> 98% at 8192.
