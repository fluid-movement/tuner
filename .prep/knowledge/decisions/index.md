* [Systematic chord namer over every root, simplest reading wins](/decisions/01M7X3VYN2B2TEHR1WRC0ZJ3RF.md) - Instead of a fixed list of chord formulas, each candidate root (every sounding pitch class) is analysed into third, fifth, seventh, 6, extensions and alterations, the name is assembled from those parts and scored by complexity (alterations, adds, missing third, root not lowest); the lowest score is the name, the next ones are alternatives. Any combination of notes gets a name, which a formula list can't guarantee (user asked for 'pretty much any combination').

* [tuner-core builds with opt-level s](/decisions/01M7X9H5ZTX0XBTXJBDR7G45WG.md) - Spectral flux onsets pushed tuner.wasm to 162.3 KB / 60.8 KB gz, over the 160/60 KB budget. Building tuner-core with opt-level "s" gives 154.7 / 58.6 KB with no measurable slowdown (chord_eval 2.0 -> 2.3 ms, poly_eval guitar 11.5 -> 9.8 ms per analysis). Alternative considered: hand-shrinking the flux code (a few KB at most).
* [Strum onsets: spectral flux alongside the envelope rule, with a slow noise floor](/decisions/01M7XA5W32PQRBAW6XR1PFADT3.md) - The envelope rule (8 dB rise) misses re-strums over ringing strings; spectral flux (mean dB rise over 80 Hz-4 kHz vs 30 ms earlier, peak >= 4 dB and 1.5 dB over the recent median) catches them. Its loudness gate uses a 30 s noise floor because the 2 s onset background climbs to the music during continuous playing. FLUX_MIN 2-3 dB let partial beating trigger onsets; 4 dB did not. The envelope rule stays for strums from silence.
* [Chord confidence: tonal crest, explained share, harmonics per string](/decisions/01M7XA5W5FW5NE0GD005A8HG9P.md) - detect_chord reports nothing unless the spectrum's loudest bin is >= 25 dB above its median (strums >= 39, noise <= 12), the tab explains >= 75% of peak weight (strums >= 0.84) and every played string explains >= 2 peaks. Explained share alone left 8 of 81 noise chords; the crest test removed the rest without touching chord_eval accuracy.
* [Chord mode: reject voices, glides and single pitches before naming](/decisions/01M7XBG4N387B0J7SCJA6CX0RR.md) - User reported chords shown with nothing played. Beyond the confidence gate, detect_chord now also rejects: a strong peak below the instrument's lowest note (voices), readings whose notes are all one pitch's overtones (hummed or sung notes, single plucked strings), fundamentals wider than a steady string's peak (glides), and fundamentals less than 20 dB above local background; the listener requires -55 dBFS for an onset and stage agreement. A single plucked note no longer shows in chord mode (chord mode is for chords). Alternatives: a higher onset threshold alone would also drop quiet real strums.
* [Audio thread runs pitch detection only in String mode](/decisions/01M7XCFJTX1WEP5RNE74KYDWGD.md) - Chord and Strum modes only need the level for the meter, so the worklet calls MonoTuner::process_level (wasm tuner_set_pitch 0) and posts every other frame; this saves ~35 ms of analysis per audio second (native) on the audio thread. Switching back to String mode re-enables detection; a note already sounding locks via the steady path (0.15 s).
* [No float clamp in tuner-core: use max/min](/decisions/01M7XCFJXPPZ043QB6Z1MTF2XA.md) - f32/f64::clamp's panic message pulls float formatting (~14 KB of dragon/grisu code) into tuner.wasm; replacing the two calls with max/min took the module from 161.2 to 135.5 KB. Keep panicking float formatting (clamp, {:?} of floats in asserts) out of non-test core code; check with twiggy when the wasm grows unexpectedly.
